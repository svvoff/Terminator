# TASK-005 — Apple Events consent: pre-warm, per-app state, deep link

## Why deferred

**Deferred 2026-08-28 by the author, on TASK-009's measurement.** This card exists to keep the
OS consent dialog away from the moment of closing. TASK-009 measured that no dialog appears
there: the hand-rolled quit is sent with `kAEDoNotPromptForUserConsent`, consent is never
consulted, and the target dies whether consent was never asked or **explicitly denied** —
seventeen sends across five applications spanning first-party/third-party,
sandboxed/unsandboxed, Mac App Store/direct, document-based/not and scriptable/not
(findings §5). There is nothing to pre-warm and no denial to route around.

The one piece of this card with surviving value — `NSAppleEventsUsageDescription`, which macOS
renders verbatim if a dialog is ever raised — already shipped in `Packaging/Info.plist` with
TASK-002.

**The ten-section contract below is left intact rather than stripped**, against the shape
`backlog/index.md` describes for deferred cards. Deleting a written contract to satisfy a
template would cost work and buy nothing. But it is **not** promotable as written: promoting it
means re-deriving the whole card against findings §5 as it now reads, not moving the file back.

What would bring it back: the product sending an Apple Event that is **not** `'aevt'/'quit'`,
or a macOS release that puts the gate back on the quit path. Either is a new measurement, not a
guess.

## Goal

Hold and model the Apple Events consent that DEC-002's polite quit depends on, and acquire it at
a moment the user can make sense of — adding the app, or the app's first observed launch — never
at the moment of closing.

This card produces the consent state, the pre-warm entry point, the deep-link URL and the log.
It renders nothing: every popover row that shows consent state belongs to TASK-006.

## Context

`'aevt'/'quit'` is not on the consent-exempt Apple Event list, and consent is granted per
(client, target) pair: every watched app needs its own grant (see findings §5). Consent is
therefore a first-class feature of this product, not an implementation detail of the quit call.

Three facts from findings §5 fix the shape of this task:

- The default moment for the prompt is kill time, and `AESendMessage` blocks the calling thread
  until the user answers. A dialog immediately before an app closes is exactly what DEC-004
  forbids.
- `AEDeterminePermissionToAutomateTarget` can only prompt for a **running** target; a
  non-running one returns `procNotFound (-600)`. Consent cannot be acquired at all for an app
  that is closed when the user adds it.
- On denial `AESendMessage` returns `errAEEventNotPermitted (-1743)` forever. Denial is a
  terminal state, not a retry case (DEC-002).

The one-time system prompt this task produces is **not** a DEC-004 violation. DEC-004 says so
explicitly: it is generated by macOS, not by our code, and moving it away from the moment of
closing is this card's entire purpose.

**The failure mode this card exists to prevent.** Observation costs no permission at all
(findings §1): detecting launches, counting down and recording focus all work with every TCC
grant denied. Only the quit needs consent. So an app whose quit is never permitted is watched
correctly, counted down correctly, and simply never closes — and because DEC-004 means there is
no warning UI that could be missing, this produces **zero symptoms**. The tool looks like it is
working. That is why per-app consent state must be computed here and rendered by TASK-006,
rather than discovered in the log after the fact.

**Split with TASK-006.** This card owns the computation: the `OSStatus` → state mapping, the
pre-warm entry point, the deep-link URL, and the log lines. TASK-006 owns every pixel: the row
that shows a state, the control that opens the deep link, and the manual checks that assert
anything about a popover row. This card's own evidence is the log, so it can be built and
verified before any popover exists.

TASK-001 settles open questions 2 and 4 (a missing `NSAppleEventsUsageDescription`; pre-warming
with `askUserIfNeeded: true` on a background queue). This card consumes those answers.

## Scope

**Consent state as a pure mapping.** A `TerminatorCore` type maps an `OSStatus` from
`AEDeterminePermissionToAutomateTarget(askUserIfNeeded: false)` to a consent state:

| `OSStatus` | State |
|---|---|
| `noErr` (0) | `ready` |
| `errAEEventWouldRequireUserConsent` (-1744) | `notAsked` |
| `errAEEventNotPermitted` (-1743) | `denied` |
| `procNotFound` (-600) | `targetNotRunning` |
| anything else | `unknown(OSStatus)` |

The mapping is total, synchronous, Foundation-only and has no AppKit dependency. `unknown`
carries the raw status so the log can name it.

**Consent state is never persisted.** It is recomputed on demand, because the user can change
an Automation grant in System Settings at any time and the config file would go stale silently.
The rule store (TASK-003) holds rules; it does not hold consent.

**Pre-warm, on a background queue, at two moments and no others.**

- *Add-app time*, if the target is running: call
  `AEDeterminePermissionToAutomateTarget(askUserIfNeeded: true)` for that target's pid. The
  add-app UI belongs to TASK-006; it calls this entry point.
- *First observed launch of a watched app*, if consent is still `notAsked`: same call. This is
  the only path available for an app that was closed when the user added it.
- **Never at expiry.** No code path may reach a prompting call from the expiry action.

**The first-launch trigger is a named seam, not a hand-off.** TASK-004's engine emits
`.appFirstObserved(bundleIdentifier:pid:)` the first time a watched bundle identifier is
observed running in this Terminator session. This card's pre-warm entry point takes exactly that
payload — a bundle identifier and a pid — so the effect handler can call it directly. This card
does not reach into the `NSWorkspace` observer, does not add its own launch detection, and does
not read `runningApplications` to find out when an app started.

A one-time dialog seconds after the user themselves opened the app is far less hostile than one
at kill time. The grant is keyed to the target's bundle identifier, so it is acquired once and
holds across every later relaunch of that app.

Both the prompting and non-prompting determinations run off the main thread, for the same
reason the quit send does (findings §4, §5): they block the calling thread.

**The deep-link URL is a value this card owns.** The URL that opens System Settings →
Privacy & Security → Automation
(`x-apple.systempreferences:com.apple.preference.security?Privacy_Automation`) is exposed as a
constant alongside the consent state, and this card verifies that it actually lands on the
Automation pane on macOS 26. If it does not, find the URL that does, use it, and record it in
the execution log. The control that opens it is TASK-006's.

**One condition, one story.** When the engine produces a terminal
`refused(errAEEventNotPermitted)` (TASK-004) the consent state for that app is `denied`. They
are the same condition seen from two sides. This card states that equivalence so TASK-006 can
render it as one problem rather than two.

**Logging.** Every consent transition is logged with `os.Logger` at `.notice`, using the shared
subsystem constant `com.svvoff.terminator` (the hardcoded identifier constant, findings §11) and
the category `consent`. Every interpolated value carries `privacy: .public`, including the
bundle identifier and the raw `OSStatus` (findings §14). Because there is no warning UI, the log
is the entire answer to "why did my app not close" — and for this card it is also the entire
evidence trail.

**Info.plist precondition.** `NSAppleEventsUsageDescription` is authored by TASK-002. Verify it
is present before doing anything else: without it the prompt never appears and every quit fails
forever (findings §5). If it is absent, stop and report — do not work around it here.

## Non-goals

- No onboarding screen, permission card or welcome flow. Watching and focus recording need no
  permission at all (findings §1) and the recon removed this from scope.
- **No UI of any kind.** No popover row, no view, no view-model formatting of a consent state.
  Rendering consent — including the `denied` and `notAsked` rows and the deep-link control — is
  TASK-006.
- No prompting at expiry, under any condition.
- No retry of a denied event. `-1743` is terminal (DEC-002).
- No notification, alert or HUD of our own about consent state (DEC-004).
- No attempt to detect, work around or re-request a revoked grant automatically beyond
  recomputing state.
- Not the quit send itself, and not the retry loop — those are TASK-004.
- Not launch detection. `.appFirstObserved` is TASK-004's to emit.

## Acceptance criteria

- A `TerminatorCore` test suite `ConsentStateTests` asserts the full `OSStatus` → state mapping
  above, one named test per row: `noErrMapsToReady`, `wouldRequireUserConsentMapsToNotAsked`,
  `notPermittedMapsToDenied`, `procNotFoundMapsToTargetNotRunning`, and
  `unlistedStatusMapsToUnknownCarryingThatStatus`. The suite imports Foundation only, needs no
  running app, no real Apple Event and no sleeps.
- A named test `deniedIsTheSameConditionAsRefused` asserts that the state derived from
  `errAEEventNotPermitted` and the state derived from TASK-004's terminal
  `refused(errAEEventNotPermitted)` are equal, so the two cannot drift apart.
- The pre-warm entry point takes `(bundleIdentifier: String, pid: pid_t)` — the payload of
  TASK-004's `.appFirstObserved(bundleIdentifier:pid:)` — so the effect handler calls it with no
  adaptation.
- The pre-warm entry point begins with `dispatchPrecondition(condition: .notOnQueue(.main))`,
  so a main-thread call traps in debug rather than blocking the UI.
- A grep of the sources shows no call site reaching `askUserIfNeeded: true` from the expiry
  action or from any code owned by the expiry strategy.
- A grep of the sources shows no SwiftUI type introduced by this task.
- Consent state appears in no persisted DTO. The config file written by TASK-003 is unchanged
  by this task.
- Every `os.Logger` interpolation added by this task carries `privacy: .public`, and every
  logger uses the shared subsystem constant with category `consent`.
- A manual checklist, checked in with the card's evidence, covers with concrete observable steps.
  At this card's dependency level there is no popover and no engine, so the pre-warm entry point
  is driven by a temporary call from the app's startup path, removed before the card is
  accepted; the log excerpt is the evidence. The steps:
  1. With a rule hand-written into the config file for an app that is currently running,
     launching the bundle produces the real macOS Automation prompt, and the log records the
     transition with the bundle identifier readable (not `<private>`).
  2. Denying the prompt makes a fresh determination return `errAEEventNotPermitted (-1743)`, and
     the log records `denied`.
  3. Granting from System Settings → Privacy & Security → Automation makes a fresh determination
     record `ready` without restarting Terminator, showing that state is recomputed and never
     persisted.
  4. A determination for a watched app that is not running records `targetNotRunning` and
     produces no prompt.
  5. `open 'x-apple.systempreferences:com.apple.preference.security?Privacy_Automation'` lands
     on the Automation pane on macOS 26. Record the URL that works.
  6. No prompt appears at any moment other than the two named above.

## Validation requirements

- `swift build` and `./build.sh` green; `codesign --verify --strict` is the build's terminal
  step and its exit code.
- `swift test` green, including `ConsentStateTests`.
- Manual checklist executed against `./build/Terminator.app/Contents/MacOS/Terminator`. Never
  `swift run` — a bare executable is `.prohibited` and can never show a menu bar item
  (findings §7).
- Log evidence is read back with, verbatim:
  `log show --predicate 'subsystem == "com.svvoff.terminator"' --style compact --last 1h`
  (`.notice` persists and needs no `--info`, findings §14).
- The checklist must be run under the stable self-signed identity from TASK-001/TASK-002.
  Under ad-hoc signing every rebuild re-prompts and the results are meaningless (findings §6).

## Executor allowed areas

- New consent files in `TerminatorCore` (Foundation only; no AppKit, no `defaultIsolation`),
  including the state type, the mapping and the deep-link URL constant.
- The adapter target created by TASK-002, for the `AEDeterminePermissionToAutomateTarget`
  wrapper and its background dispatch.
- Tests for the mapping.
- The manual checklist file that this card's evidence points at.

## Executor forbidden areas

- Any SwiftUI view, any popover row, any view-model formatting of consent state. That is
  TASK-006's half of this feature; this card's evidence is the log.
- The bundle's `Info.plist` (owned by TASK-002). If `NSAppleEventsUsageDescription` is missing,
  the task is blocked, not fixed here.
- `build.sh` and the signing step.
- The quit send and the retry loop (TASK-004).
- The engine reducer, its `EngineInput` and `Effect` enums, and the `NSWorkspace` observer
  (TASK-004). If `.appFirstObserved`'s payload does not fit, escalate rather than adding a
  second launch-detection path here.
- The on-disk config schema (TASK-003).
- `NSRunningApplication.terminate()` in any form (findings §4, DEC-002).
- `swiftLanguageMode(.v5)`, `@preconcurrency import`, `@unchecked Sendable`.

## Orchestrator review focus

- Is the mapping total, pure and synchronous, or has an async determination leaked into Core?
- Can any expiry path reach a prompting call?
- Does the pre-warm actually run off the main thread, or only claim to?
- Does the first-launch path consume `.appFirstObserved`, or has this card grown its own launch
  observation?
- Is consent state absent from everything written to disk?
- Did any rendering leak in? A view file in this card's diff is a scope violation, not a
  convenience.
- Does every added log line carry `privacy: .public`, the shared subsystem constant, and the
  `consent` category?
