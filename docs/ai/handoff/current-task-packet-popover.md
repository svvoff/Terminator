## Почему раунд 6

Решение автора. Строки списка **двигаются**: `PopoverViewModel` сортирует по бакету `sortRank`, а
внутри бакета по остатку времени, и все эти входы меняются при открытом поповере — отсчёт тикает
каждую секунду, приложение запускается и выходит, тумблер щёлкает. Тумблер уезжает из-под курсора
ровно тогда, когда правило собираются выключить, а это по DEC-006 единственный рычаг, на который
пользователь имеет право.

Автору названа цена буквального «порядка добавления»: его нет на диске — `rules` это JSON-объект
с ключом по bundle id, поля `addedAt` нет, — и он потребовал бы смены формата файла и миграции.
Автор эту цену платить не стал и выбрал **стабильный порядок по bundle id**.

## Что менять

**Сортировка строк становится: по `bundleIdentifier`, по возрастанию, и больше ничем.**

Убирается `sortRank` и вся бакетизация (запущенные / без экземпляра / выключенные) и сортировка
по остатку. Второго ключа не остаётся — сортировать больше не по чему.

Бакеты убираются намеренно, а не сохраняются «как вторичный признак»: уцелевший бакет — это
бакет, между которыми строка может переехать, а переезжающая при щелчке тумблера строка
воспроизводит ровно ту помеху, ради устранения которой раунд и делается.

**Экземпляры внутри строки** сортируются по `SessionKey` (`PopoverViewModel.swift:41`) — это
другой список, он уже детерминирован, его не трогать.

**Не сортировать по имени приложения.** Имя резолвится из окружения (амендмент 5), и порядок строк
начал бы зависеть от того, что установлено на машине и на каком языке система. Порядок не должен
быть функцией чего-либо вне файла правил.

## Тесты: четыре вычёркиваются, три добавляются

Вычеркнуть — они запирают ровно то поведение, которое убирается
(`Tests/TerminatorCoreTests/PopoverViewModelTests.swift`, строки 64, 85, 103, 121):

- `rowsSortAscendingByRemainingTime`
- `rulesWithNoRunningInstanceSortAfterRunningOnes`
- `disabledRulesSortLast`
- `equalRemainingTimesBreakTieByBundleIdentifier` — поглощён: при одном ключе ломать нечего

Добавить три, и они проверяют **саму стабильность**, а не только ключ сортировки. Тест, который
проверяет один ключ, прошёл бы и на реализации, которая всё ещё переупорядочивает по другому
входу:

1. `rowsSortByBundleIdentifierAscending` — порядок это bundle id по возрастанию, и ничто другое на
   него не влияет;
2. `rowOrderDoesNotChangeAsRemainingTimeChanges` — те же правила, вычисленные при двух разных
   `now` с отсчётами в разных точках, дают один и тот же порядок;
3. `rowOrderDoesNotChangeWhenARuleIsDisabledOrItsAppExits` — выключение правила и снятие его
   запущенного экземпляра каждое по отдельности порядок не меняют.

**Число тестов идёт с 83 на 82.** Это ожидаемо: минус четыре, плюс три. Другое число — стоп.
